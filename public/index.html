Dynamic Function Table RF_CALLBACK Injection

post @ 2026-09-06

Dynamic Function Tables & the RF_CALLBACK (Type 2) Mechanism

On x64 Windows, stack unwinding for exceptions and SEH is table-driven, not frame-pointer-based. Every function that touches the stack must have a RUNTIME_FUNCTION entry (.pdata) describing its prologue/epilogue so the unwinder can walk the stack.

For statically compiled modules, RtlLookupFunctionEntry() finds these tables via the PE’s IMAGE_DIRECTORY_ENTRY_EXCEPTION. But for JIT-compiled code (CLR, Java, JavaScript engines, dynamically generated stubs), Windows exposes an API to register unwind info at runtime:

  • RtlAddFunctionTable() — Type 1 (static table in memory)
  • RtlInstallFunctionTableCallback() — Type 2 (RF_CALLBACK) aka the interesting one
  • RtlAddGrowableFunctionTable() — Type 3

From Microslop’s own documentation:

For dynamically generated functions [JIT compilers], the runtime to support these functions must either use RtlInstallFunctionTableCallback or RtlAddFunctionTable to provide this information to the operating system. Failure to do so results in unreliable exception handling and debugging of processes.

Internally these all populate the process-global list ntdll!RtlpDynamicFunctionTable (a doubly linked list guarded by RtlpDynamicFunctionTableLock, an SRW lock).
